# 求职联系助手 P0 信任闸门设计规格

> 日期：2026-07-24  
> 状态：规格已批准；开发及 P0-01～P0-07 自动验收通过；P0-08 待测试账号真机验收  
> 适用版本：v0.3.5 之后的首个 P0 发布候选版本

## 1. 背景

现有产品已经具备以下安全底座：

- 审核列表默认不勾选，只联系人工选中的岗位。
- 发送前匹配当前岗位、公司或 HR；目标不确定时不发送。
- 招呼语采用 Enter 与发送按钮互斥的单次提交，发送结果未知时不自动重放。
- 建联后原子写入去重记录和今日计数。
- 运行中锁定平台，停止可取消等待和网络请求。
- Service Worker 意外中断后进入阻塞态，不自动恢复外部动作。

当前 P0 缺口是：侧边栏点击“联系已选”后会直接发送 `START_DELIVER`，用户看不到本批次的最终执行计划，后台也没有强制要求一个不可重放的确认意图。错误主要进入技术日志，没有稳定的错误代码、恢复建议和无障碍状态表达。

## 2. 开源对照

本设计只借鉴可复用的产品和安全模式，不复制整套实现：

- [JobMatchAI](https://github.com/wadekarg/JobMatchAI)：写入表单前展示逐项审核结果，用户一次确认后才应用。
- [BossAssistant](https://github.com/CSUlyc/BossAssistant)：运行可暂停、停止，失败和投递结果可追踪。
- [boss_batch_push](https://github.com/yangfeng20/boss_batch_push)：历史修复记录包含重复投递和重复招呼语，说明去重和一次性执行必须由运行层强制保证。
- [get_jobs](https://github.com/loks666/get_jobs)：公开记录 Boss 检测变化和智联投递故障，说明自动化测试不能替代真实招聘网站验收。

## 3. 产品目标

用户可以一次勾选多个岗位，只确认一次批次计划；确认后系统逐个岗位执行安全校验。任何绕过确认、重复确认、确认过期、平台变化、岗位缓存变化、额度不足或运行状态不确定，都必须拒绝或停机，且不得自动重放外部动作。

### 3.1 成功标准

1. 没有后台签发的一次性确认意图，联系任务不能启动。
2. 一个确认意图最多启动一次联系任务。
3. 确认前不发生打开岗位、点击沟通、投递或发送消息等外部动作。
4. 批次确认后，每个岗位仍执行平台、缓存、去重、日限、页面和目标会话校验。
5. 失败信息同时包含稳定错误代码、人类可读原因和明确的下一步操作。
6. 自动化证据与测试账号真机证据分开记录。

## 4. 非目标

本轮不实现：

- 猎聘适配器。
- 新手引导重构。
- 求职历史、CRM、跟进提醒或统计分析。
- HR 自动回复。
- 多平台并行扫描或混合批次。
- 验证码破解、隐身、指纹伪造或其他对抗平台风控的能力。
- 更换前端框架或重构全部侧边栏代码。

## 5. 用户流程

### 5.1 批次准备

1. 用户在当前平台审核列表勾选一个或多个岗位。
2. 用户点击“联系已选（N）”。
3. 侧边栏向后台发送 `PREPARE_DELIVERY`，只携带当前勾选的岗位 ID。
4. 后台根据当前平台、扫描缓存、去重记录、今日用量和运行状态生成执行计划。
5. 计划合法时，后台保存一个两分钟有效、只能消费一次的确认意图，并返回确认单。
6. 计划不合法时，不创建确认意图，返回错误代码、原因和恢复建议。

### 5.2 批次确认

确认单必须显示：

- 当前平台。
- 用户选择的岗位数。
- 实际可联系的岗位数。
- 已联系过并被排除的岗位数。
- 今日已联系数、每日上限和确认后的预计剩余额度。
- 预计等待时长范围；明确说明该估算只包含配置中的联系间隔与批次休息，页面加载可能增加总时长。
- 简历图片状态：将尝试发送 / 未配置。
- 招呼语状态：按当前平台能力生成或使用模板。
- 岗位清单：岗位名和公司；清单可滚动，不要求用户逐岗点击确认。

用户只有两个动作：

- “确认联系这 N 个岗位”：消费确认意图并启动任务。
- “返回审核”：撤销确认意图，不启动任务。

点击遮罩、按 Escape 或点击“返回审核”均视为取消；取消后必须重新准备批次才能启动。

### 5.3 后台执行

确认后后台使用意图中冻结的岗位 ID，不重新读取侧边栏当前勾选状态。每个岗位执行前继续检查：

- 岗位属于意图指定的平台。
- 岗位仍存在于同一平台的扫描缓存。
- 岗位未被当前平台的 `processed` 标记。
- 当前平台今日用量未达到上限。
- 页面未要求重新登录、未出现验证码或平台限制。
- 建联后的当前会话与岗位、公司或 HR 身份一致。

单个岗位普通失败时记录失败并继续下一个；以下情况停止整批：

- 平台或缓存不一致。
- 验证码、账号限制或登录失效。
- 目标会话身份不确定。
- 发送结果未知。
- Service Worker 中断或运行状态损坏。

## 6. 确认意图模型

确认意图保存在 `chrome.storage.local` 的 `sw_pending_delivery`，结构如下：

```js
{
  id: "intent-<opaque>",
  platformId: "boss",
  jobIds: ["job-1", "job-2"],
  createdAt: 1721820000000,
  expiresAt: 1721820120000,
  status: "pending",
  summary: {
    selectedCount: 2,
    executableCount: 2,
    skippedProcessedCount: 0,
    usageCount: 4,
    dailyLimit: 20,
    remainingAfter: 14,
    estimatedMinSec: 10,
    estimatedMaxSec: 25,
    sendsResumeImage: true
  }
}
```

约束：

- 有效期固定为 120 秒。
- `jobIds` 去重后仍为空时拒绝准备。
- 岗位 ID 不存在或属于其他平台时拒绝整个批次。
- 已联系岗位从计划中排除，并在确认单中显示数量。
- 实际可联系岗位数大于今日剩余额度时拒绝整个批次，要求用户减少选择；系统不擅自决定截断哪些岗位。
- 消费时将状态原子改为 `consumed`，然后才允许调用联系状态机。
- 已消费、已取消、已过期或找不到的意图都不得启动联系。
- 新建意图会覆盖并取消同一扩展中此前未消费的意图。

## 7. 模块边界

### 7.1 `src/delivery-guard.js`

独立 UMD 模块，浏览器和 Node 测试共用，负责：

- 规范化并去重岗位 ID。
- 根据岗位缓存、平台配置、去重记录和日限生成批次计划。
- 计算间隔与批次休息的最小/最大估算时间。
- 创建、取消和一次性消费持久确认意图。
- 返回稳定错误代码，不操作招聘网站。

### 7.2 `src/background.js`

新增两个消息入口：

- `PREPARE_DELIVERY`：加载固定快照，调用 `DeliveryGuard.prepare`，保存意图并返回确认单。
- `CONFIRM_DELIVERY`：消费意图，重新校验平台、缓存和额度，然后用冻结的岗位 ID 调用 `runDeliver`。

原有 `START_DELIVER` 不再启动任务，只返回 `CONFIRMATION_REQUIRED`。这样即使旧版侧边栏、重复点击或其他扩展内部页面直接发送旧消息，也不能绕过确认。

`runDeliver` 保留现有逐岗安全检查、原子联系记账和未知结果不重试逻辑。

### 7.3 `src/sidepanel.html` / `src/sidepanel.js` / `src/sidepanel.css`

新增批次确认对话框和阻塞恢复卡片：

- 对话框使用 `role="dialog"`、`aria-modal="true"`、标题和说明关联。
- 打开时焦点进入确认单；Tab 焦点留在对话框内。
- Escape、返回审核和遮罩取消意图。
- 确认按钮在请求期间禁用，避免重复提交。
- 日志使用 `role="log"` 和 `aria-live="polite"`。
- 阻塞恢复卡片使用 `role="alert"`，显示原因和下一步操作。
- 恢复建议可以引导用户返回审核、重新扫描、登录平台或打开平台页面核对。
- 所有输入控件使用显式 `for` / `id` 关联；恢复可见焦点样式。

## 8. 错误模型

| 错误代码 | 用户文案 | 下一步 |
|---|---|---|
| `NO_SELECTION` | 尚未选择岗位 | 返回审核并勾选岗位 |
| `STALE_REVIEW` | 岗位列表已变化，无法确认当前批次 | 重新扫描 |
| `PLATFORM_MISMATCH` | 岗位与当前平台不一致 | 重新扫描当前平台 |
| `NO_AVAILABLE_JOBS` | 所选岗位都已联系过 | 返回审核或重新扫描 |
| `DAILY_LIMIT_REACHED` | 今日联系额度已用完 | 明日再试 |
| `DAILY_LIMIT_EXCEEDED` | 所选岗位超过今日剩余额度 | 减少选择后重试 |
| `CONFIRMATION_REQUIRED` | 联系前必须先确认批次 | 重新打开确认单 |
| `INTENT_NOT_FOUND` | 确认单已失效 | 重新确认 |
| `INTENT_EXPIRED` | 确认已超过两分钟 | 重新确认 |
| `INTENT_ALREADY_USED` | 该批次已经启动过 | 查看执行状态 |
| `LOGIN_REQUIRED` | 当前平台登录已失效 | 登录后重新扫描 |
| `SELECTOR_UNAVAILABLE` | 招聘网站页面已变化，无法安全定位操作 | 停止使用该平台并更新适配器 |
| `TARGET_UNCERTAIN` | 无法确认当前会话对应的岗位或公司 | 在平台中人工核对，不自动发送 |
| `SEND_RESULT_UNKNOWN` | 无法确认消息是否已发送 | 在平台中人工核对，不自动重试 |
| `SERVICE_WORKER_INTERRUPTED` | 浏览器后台意外中断 | 核对平台记录后重新扫描 |

## 9. P0 验收标准

### P0-01 批次一次确认

- 勾选多个岗位后只出现一个确认单。
- 确认单列出全部实际可联系岗位，不要求逐岗确认。
- 取消确认不产生任何招聘网站操作。

### P0-02 后台强制确认

- 直接发送旧 `START_DELIVER` 返回 `CONFIRMATION_REQUIRED`。
- 没有意图、意图过期、意图已消费或意图 ID 错误均不能启动任务。
- 双击确认最多启动一个任务。

### P0-03 冻结批次与逐岗校验

- 后台只执行意图内冻结的岗位 ID。
- 确认后切换平台、修改缓存或岗位已被处理时，任务拒绝或停机。
- 每个岗位执行前重新检查日限和去重。

### P0-04 额度与去重

- 已联系岗位不进入实际计划，确认单显示排除数量。
- 所选可联系岗位超过剩余额度时整个批次不能开始。
- 建联成功或结果不确定后，去重记录与今日计数保持一次写入；重复执行不增加计数。

### P0-05 未知结果与中断

- 发送结果未知时不重试当前岗位并停止整批。
- Service Worker 遗留运行记录恢复为阻塞态，不恢复或重放外部动作。
- 阻塞原因和恢复建议在侧边栏可见。

### P0-06 可访问性

- 确认单可以只用键盘完成确认或取消。
- 对话框打开和关闭后焦点位置合理。
- 输入标签与控件关联。
- 焦点样式可见。
- 日志和阻塞状态具有辅助技术可读取的语义。

### P0-07 自动化验证

必须新增并通过：

- 批次计划：去重、跨平台、缺失岗位、全已处理、额度用尽、超过剩余额度。
- 时间估算：单岗位、普通间隔、跨批次休息。
- 意图存储：创建、覆盖、取消、过期、错误 ID、单次消费、并发双消费。
- 后台契约：旧入口被拒绝；确认入口调用冻结岗位列表。
- 静态 UI：对话框语义、日志语义、显式标签和脚本加载顺序。
- 现有单次发送、原子记账、平台隔离和中断恢复测试全部回归。

自动验证命令：

```bash
npm test
for f in $(rg --files -g '*.js'); do node --check "$f"; done
python3 -m json.tool manifest.json >/dev/null
```

### P0-08 测试账号真机验收

Boss 与智联分别使用测试账号执行：

1. 登录后扫描至少 3 个岗位。
2. 勾选 2 个岗位，确认只出现一次批次确认单。
3. 取消一次，确认平台上没有产生联系或投递。
4. 再次确认，检查实际执行顺序和平台记录。
5. 运行中停止，确认下一个外部动作不再发生。
6. 人为制造登录失效或选择器找不到，检查停机文案和恢复建议。
7. 刷新或重启扩展模拟后台中断，确认不会自动重放。

真机验收涉及向招聘平台发送消息或投递，必须在测试账号和测试岗位上进行，并在动作发生前获得用户明确授权。没有测试账号或授权时，此项状态必须标为“待真机验收”，不得写成“已通过”。

## 10. 发布闸门

满足以下条件才可称为 P0 完成：

- P0-01 至 P0-07 全部有自动化或静态验证证据。
- P0-08 有真实测试账号证据，或者明确标注“待真机验收”，且版本不得宣称已完成真实平台验证。
- README、`docs/07-multi-platform-design.md` 和测试说明同步更新。
- 不存在未完成占位内容、失效链接或与代码行为矛盾的文案。
